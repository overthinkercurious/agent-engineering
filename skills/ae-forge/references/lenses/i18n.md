# Internationalization lens (text, and everything shaped by locale)

## Exclusive constraint

Adds locale depth to Experience's journey boundary and Builder's
implementation: which strings a person sees, in which language, and everything
else a locale decides — dates, numbers, currency, sorting, pluralisation, and
which direction the layout runs.

`accessibility` owns whether a person can operate the interface.
This lens owns whether the interface is correct for where they are — which
includes being wrong in ways that look fine in English.

## Activates

Signals: `i18n`, `l10n`, `internationalization`, `localization`, `locale`,
`translation`, `rtl`, `timezone`, `currency`, `pluralization`, `unicode`, or a
change that adds user-visible text, formats a date or number, or sorts strings.

Skip for internal tooling with one declared audience and no formatting of
dates, numbers or currency.

## Checklist

**Design (Architect)**

1. Name the supported locales and the fallback chain. "English for now" is a
   decision; an undeclared default is a decision nobody made.
2. Decide where formatting happens. A date formatted on the server carries the
   server's locale and timezone to every reader; formatted on the client, it
   carries theirs. Both are valid, one is usually wrong for the case.
3. For anything time-bearing, separate the instant from its presentation.
   Store an unambiguous instant; apply the timezone at the boundary where
   someone reads it. A date that means "today" depends on who is asking.
4. Decide whether right-to-left is supported. It is a layout decision, not a
   translation one, and retrofitting it means revisiting every directional
   assumption in the interface.

**Implementation (Builder)**

5. Never build a sentence by concatenation. Word order differs per language, so
   `"Deleted " + n + " items"` is untranslatable; a parameterised message is.
6. Use the platform's plural rules rather than `n === 1`. Several languages
   have more than two plural forms, and some have one.
7. Use locale-aware comparison for sorting and case operations. Byte order is
   not alphabetical order in most languages, and `toUpperCase` is
   locale-dependent in a few.
8. Format currency with its own locale and its currency code, never by
   prefixing a symbol. The symbol, its position, the decimal separator and the
   number of decimal places are all locale decisions — and the amount itself
   stays an integer in its smallest unit regardless.
9. Leave room. Translated text commonly runs longer than English, so a layout
   that only fits the English string is a layout that breaks on release.
10. Keep user-supplied text out of the translation catalogue. It is data, not
    a message, and it is not the translator's to change.

**Verification (Verifier)**

11. Render a locale that is not the development default, including one
    right-to-left locale if supported. Reasoning about it is not checking it.
12. Confirm a date near midnight renders as the correct day in a timezone that
    is not the machine's.
13. Confirm no user-visible string is missing from the catalogue — a fallback
    that silently shows a key is worse than one that shows English.

## Evidence

Name the supported locales with their source, the catalogue location, the
formatting boundary with `path:line`, and which locales were actually
rendered. State which checks were run against a rendered interface versus read
in code.

## Findings

Every finding names the locale and what the person sees. "Date handling is
locale-unsafe" is not a finding; "at `ledger.tsx:88` the day boundary uses the
device timezone, so a transaction at 23:40 IST shows on the previous day for a
reader in UTC" is.

## Authority

This lens narrows what a role must check; it never outranks the project's own
declared locales, its timezone doctrine, or an enforced gate. Where the project
fixes a single timezone deliberately, that decision wins and this lens records
the difference.

## Hands off

Does not own: keyboard operability and assistive-technology exposure
(`accessibility`), visual craft and spacing (`ui-finish`), money arithmetic and
storage type (`payments`), or the final delivery verdict (Verifier).
