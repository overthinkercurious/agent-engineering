# Discovery and evidence

Forge owns alignment with the user. Discovery ends when the relevant current
system is understood, intended behavior is explicit, and unresolved facts are
either resolved or attached to the work they block.

## Inspect, then clarify

1. Read the request, relevant project instructions and existing source. Preserve
   the dirty/untracked baseline. Reuse confirmed answers from an active run.
2. Identify the user, journey, desired result, constraints, non-goals and
   important failure behavior. Ask a small focused round only for missing
   answers that could change the result. Ask follow-ups when an answer exposes
   another material choice. Routine implementation choices belong to Forge.
3. Record the short answer and its consequence in discovery evidence; put
   accepted behavior and acceptance checks in the brief. Distinguish confirmed
   answers, inferred facts, assumptions and unresolved intent.
4. Reflect the agreed outcome before the approach checkpoint. Silence never
   supplies an answer or approval. Mark dependent work waiting; continue useful
   independent inspection.

For “add a task list,” personal versus shared ownership changes the behavior;
which internal skill to dispatch does not require a user question.

## Reconcile documents, source and runtime

Documents describe candidate intent or implementation claims. Source establishes
implemented rules; observed runtime establishes behavior for a particular
build and configuration. Neither establishes intended behavior by itself.

For a consequential contradiction, record the claim, its origin, current
source evidence, runtime evidence and whether intended behavior is resolved.
Trace whether the cause is a stale document, implementation drift, intentional
exception or a different running build. Ask the user only if inspection cannot
resolve the intended standard. Keep the affected recommendation provisional.

A timestamp is provenance, not proof. Reuse a verified fact while its relevant
source, configuration and build identity still match. Reopen it after change.
Follow project instructions; a descriptive-document conflict is not permission
to override an instruction. Flag instruction conflicts to the user.

## Research only the uncertainty

State the question and decision it affects. Prefer inspected project patterns
for local behavior, then current primary documentation for external facts.
Compare viable options against confirmed requirements; stop at an adequate
fit. Cite the source, checked date and conclusion, with limitations.
Unavailable research stays an explicit unknown. Store the findings in one
relevant contribution; a separate research agent is optional.

## Rendered applications and device tools

Inspect the connected tool's actual availability, version/help and supported
capabilities before relying on it. Confirm the selected emulator/device, app
and build identity; establish how it relates to the source being inspected.
Test navigation and screenshot/inspection access. Name missing capabilities;
a source-only assessment cannot silently satisfy an emulator audit.

Map requested screens and relevant states from navigation, source and runtime.
Record each as inspected, inaccessible or excluded with a reason. Confirm the
design baseline and intentional exceptions; inspect supported themes, widths
and text scaling relevant to scope. Screenshots establish appearance; exact
token values need source or inspectable properties, and interaction claims
need exercised actions. Revisit the user when research exposes unresolved intent.

For a requested full audit, preserve full declared coverage. A bounded first
pass is explicitly partial; report every uninspected area and remaining work.
